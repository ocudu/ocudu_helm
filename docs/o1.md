# O1 / NETCONF

**Applies to:** `ocudu-gnb`, `ocudu-cu`, `ocudu-du`, `ocudu-cu-cp`, `ocudu-cu-up`.

Each RAN chart can expose an O1 management interface: a NETCONF server that serves a
3GPP `ManagedElement` model, with an `ocudu-o1-adapter` that renders the running config
into the application's config file. O1 is off by default and in a separate values file.
Enable it by setting `o1.enable_ocudu_o1: true` and using the chart's
[`values-o1.yaml`](#enabling-o1) as a base.

## Enabling O1

O1 lives in each chart's `values-o1.yaml`. In the other four charts the `o1.*` and
`o1Config` keys are absent from `values.yaml`, so O1 is off unless they are supplied;
`ocudu-gnb` carries a small `o1:` block in `values.yaml` (`enable_ocudu_o1: false` plus TLS
keys), which likewise leaves O1 off until `values-o1.yaml` supplies the rest. Install with
that file as a base:

```yaml
# chart: ocudu-cu-cp
# with: values-o1.yaml
o1:
  enable_ocudu_o1: true
```

```bash
helm install <release> <chart> -f values-o1.yaml
```

The NETCONF server always listens on SSH (`o1.o1Port`, 830 by default), exposed by a
NodePort Service (`o1.netconfServer.service`). TLS (port 6513) is optional.

## Per-chart facts

What differs between the charts is the `ManagedElement` function the netconf-server serves
and the application config file the adapter renders. Everything else in this guide is the
same for every chart.

| Chart | Application binary | Config file (`config.*` / rendered by adapter) | `ManagedElement` function(s) |
|-------|--------------------|-------------------------------------------------|------------------------------|
| `ocudu-gnb` | `gnb` | `gnb-config.yml` | `GNBCUCPFunction`, `GNBCUUPFunction`, `GNBDUFunction` |
| `ocudu-cu` | `ocu` | `cu-config.yml` | `GNBCUCPFunction`, `GNBCUUPFunction` |
| `ocudu-du` | `odu` | `du-config.yml` | `GNBDUFunction` |
| `ocudu-cu-cp` | `ocucp` | `cu-cp-config.yml` | `GNBCUCPFunction` |
| `ocudu-cu-up` | `ocuup` | `cu-up-config.yml` | `GNBCUUPFunction` |

The `o1Config.o1-config.xml` key holds the `ManagedElement` template; it replaces the
`config` ConfigMap in O1 mode. Its default ships in each chart's `values-o1.yaml`.

## How O1 mode changes the pod

In O1 mode the pod gains two sidecars — `ocudu-o1-adapter` and `netconf-server` — and the
startup path changes:

- The `config` ConfigMap is replaced by `o1Config`, an `o1-config.xml` `ManagedElement`
  template (the per-chart function is in [Per-chart facts](#per-chart-facts)).
- The adapter renders the chart's config file (for example `cu-cp-config.yml`) from the
  NETCONF running config into a shared `emptyDir`.
- The entrypoint waits for that file (up to `CONFIG_CREATE_TIMEOUT`, 120s) before starting
  the application binary.
- Liveness tracks the adapter's `/config-healthy` endpoint instead of `pgrep` on the
  application binary.

All containers run as uid 1000.

## Ports are fixed by the images

`o1.o1Port` (830), `o1.healthcheckPort` (5000) and the TLS port (6513, hardcoded in the
templates) are **not freely configurable**, despite two of them being values. Neither
sidecar is passed a port flag: the netconf-server's listen ports and the adapter's HTTP
port are built into their images, and the chart values only tell the *other* side of each
pair where to connect.

Changing `o1.o1Port` therefore moves the Service, the `containerPort` and the adapter's
`--netconf_port`, while the server keeps listening on its built-in port. The adapter cannot
connect, `/config-healthy` never returns 200, and the pod dies on `CONFIG_CREATE_TIMEOUT`
— with nothing in the logs pointing at the port. Changing `o1.healthcheckPort` aims the
liveness probe and the entrypoint's `/restarted` notification at a closed port instead.

Treat all three as fixed unless you are also changing `o1.o1Adapter.image` /
`o1.netconfServer.image` to images that listen elsewhere. The external NodePorts
(`o1.netconfServer.service.nodePort`, 30830 by default) *are* configurable — they are the
ports outside the pod, not the ports inside it.

## The `ip_unprivileged_port_start` sysctl

All containers run as uid 1000. To let the non-root netconf-server bind `o1.o1Port` (830)
without a capability, `values-o1.yaml` sets the pod sysctl
`net.ipv4.ip_unprivileged_port_start: "0"` under `podSecurityContext`. It is a safe sysctl
on the kubelet's default allow-list, so no `allowedUnsafeSysctls` change is needed.

Kubernetes rejects `net.*` sysctls when `network.hostNetwork: true`, so O1 and
`hostNetwork` cannot be combined.

## Enabling TLS

```yaml
# chart: ocudu-cu-cp
# with: values-o1.yaml
o1:
  enable_ocudu_o1: true
  netconfServer:
    tls:
      enabled: true
      certSecret: ""  # see below
```

The o1 adapter connects to the netconf-server over **mutual TLS**, so two identities are
involved: the server's (used on port 6513) and the adapter's client identity (its cert CN
maps to the NETCONF username via `cert-to-name`).

### Option 1 — Auto-generated self-signed certs (dev/test)

Leave both `certSecret` and `clientCertSecret` empty. The netconf-server generates a
self-signed CA + server cert + client cert at startup into a shared `emptyDir`; the adapter
reads its client cert back from it. No secrets to manage.

### Option 2 — Operator-provided certs (production)

Provide **two** secrets, so neither container holds the other's private key. The server
secret is mounted read-only at `/etc/netconf-tls`; the client secret at
`/etc/netconf-tls-client`.

```bash
# server identity
kubectl create secret generic netconf-tls-certs -n <namespace> \
  --from-file=ca.crt=./ca.crt \
  --from-file=server.crt=./server.crt \
  --from-file=server.key=./server.key

# client identity (adapter). Its client.key is a privileged credential — restrict RBAC and rotate.
kubectl create secret generic netconf-tls-client-certs -n <namespace> \
  --from-file=ca.crt=./ca.crt \
  --from-file=client.crt=./client.crt \
  --from-file=client.key=./client.key
```

Then reference both in values:

```yaml
# chart: ocudu-cu-cp
# with: values-o1.yaml
o1:
  netconfServer:
    tls:
      enabled: true
      certSecret: netconf-tls-certs
      clientCertSecret: netconf-tls-client-certs
```

`clientCertSecret` is required whenever `certSecret` is set — rendering fails with a clear
message otherwise. The server uses its secret as-is without generating new certs.

### Reaching the TLS port from outside

With TLS enabled the Service gains a second port for 6513 alongside the SSH port. On a
NodePort Service its external port is `o1.netconfServer.tls.tlsNodePort`; leave it empty and
Kubernetes assigns one from the NodePort range automatically. This is separate from
`o1.netconfServer.service.nodePort`, which is the external port for the SSH endpoint (830)
only — it does not cover 6513.

```yaml
# chart: ocudu-cu-cp
# with: values-o1.yaml
o1:
  netconfServer:
    service:
      type: NodePort
      nodePort: 30830      # external SSH port (-> 830)
    tls:
      enabled: true
      tlsNodePort: 30613   # external TLS port (-> 6513); omit to let Kubernetes choose
```

## Provisioning the SSH host key

The netconf-server's host key is generated when its image is built, so it is the same in
every pod on a given tag and different after every rebuild — breaking any client that pins
it, such as an SMO reaching the server through the NodePort.

Supply your own to decouple the server's identity from the image tag:

```bash
ssh-keygen -t ed25519 -N "" -f ./ssh_host_ed25519_key

# the adapter verifies against this; the port must match o1.o1Port
printf '[%s]:%s %s\n' localhost 830 "$(cut -d' ' -f1,2 ./ssh_host_ed25519_key.pub)" > ./known_hosts

kubectl create secret generic netconf-ssh-hostkey -n <namespace> \
  --from-file=ssh_host_ed25519_key=./ssh_host_ed25519_key \
  --from-file=known_hosts=./known_hosts
```

```yaml
# chart: ocudu-cu-cp
# with: values-o1.yaml
o1:
  netconfServer:
    ssh:
      hostKeySecret: netconf-ssh-hostkey
```

The entry name picks the key type: the server installs the first of `ssh_host_ed25519_key`,
`ssh_host_ecdsa_key`, `ssh_host_rsa_key` it finds. Use ed25519 or ecdsa — an RSA key is
recorded in `known_hosts` as `ssh-rsa` but offered as `rsa-sha2-512`/`rsa-sha2-256`, so the
adapter refuses to verify it and will not start.

One secret, two mounts: the private key goes only to the netconf-server (at
`/etc/netconf-ssh`, mode `0400`, which the kubelet widens to `0440` and chowns to the pod's
fsGroup), the adapter gets only `known_hosts` and `--netconf_hostkey_verify`. The server
logs the fingerprint of the key it installs. Leaving `hostKeySecret` empty keeps the
image's key and no verification.

The netconf-server image must support `--ssh-hostkey-dir`. One without it exits at start
with `Unknown option '--ssh-hostkey-dir'`.

The adapter reaches the netconf-server over `localhost` inside the pod, so this mainly buys
a stable identity for external clients — it is not what stops an attacker with code
execution in the pod.

## NETCONF SSH login

The o1 adapter and external clients log in to the netconf-server as the user in
`o1.netconfServer.ssh.username`, an `ietf-ssh-server` local user with password
authentication (RFC 9644). The chart maps `NETCONF_SSH_USERNAME`/`NETCONF_SSH_PASSWORD` onto
the netconf-server container, whose `setup_ssh_user.sh` creates the user and its
`ietf-netconf-acm` write grant at startup. It passes the same user and password to the o1
adapter as `--netconf_username` and `--netconf_password`.

`values-o1.yaml` sets `username: netconf` and no password, so the chart generates a random
one (see [Password lifecycle](#password-lifecycle)). The username is required unless
`o1.netconfServer.tls.enabled` is true: rendering fails without it, because the adapter would
otherwise fall back to `root`/`root`. From the netconf-server image that removes the default
logins on (ocudu_netconf#18), this user is the only SSH login.

### Password lifecycle

The password never appears in the pod spec: both containers read it from a Secret via
`secretKeyRef`.

1. **Default:** leave `password` and `passwordSecret` empty. On install the chart generates a
   random 32-character password into a Secret named `<release>-<chart>-netconf-ssh-credentials`, and on upgrade it reads
   the password back from that Secret, so it stays the same. `helm template` cannot read the
   cluster, so a tool that renders with it (Argo CD) gets a new password on every render; use
   `passwordSecret` there.

2. **Production:** create the Secret yourself and name it in `passwordSecret`; the chart then
   creates no Secret of its own. The o1 adapter logs in with this value, so it must be the
   cleartext password, not a crypt hash:

   ```bash
   kubectl create secret generic netconf-ssh-credentials -n <namespace> \
     --from-literal=password="$(openssl rand -base64 24)"
   ```

   ```yaml
   # chart: ocudu-cu-cp
   # with: values-o1.yaml
   o1:
     netconfServer:
       ssh:
         username: netconf
         passwordSecret: netconf-ssh-credentials
   ```

3. **Dev/test:** set `password` to a fixed value, and the chart renders it into its own
   Secret. The cleartext then also sits in the chart values and in Helm's release metadata.

The Secret must exist with key `password` before the pod starts, in the release's namespace.
A changed Secret alone does not restart anything: run
`kubectl rollout restart deployment/<release>-<chart>` (or delete the pod) to apply a rotated
password.

### Connecting a password-only client

External clients reach the server via the NodePort (`o1.netconfServer.service.nodePort`,
30830 in the O1 profile). Read the password from the Secret and log in with the user:

```bash
kubectl get secret <secret-name> -n <namespace> -o jsonpath='{.data.password}' | base64 -d
ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no \
    -p 30830 <username>@<node-ip>   # smoke test; "shell request failed" after login = auth OK
```

## Persistent sidecar logs

By default the o1 adapter and netconf-server only log to pod stdout, so their output is lost
when the pod is replaced — unlike the application logs, which are written to
`persistence.mountPath`. Both sidecars can tee their stream to that same volume:

```yaml
# chart: ocudu-cu-cp
# with: values-o1.yaml
o1:
  o1Adapter:
    fileLog:
      enabled: true
      filename: o1-adapter.log
  netconfServer:
    fileLog:
      enabled: true
      filename: netconf.log
```

All containers mount the shared `ocudu-logs` volume, so the files land next to the
application logs:

```
/var/log/ocudu/
├── 20260730-121500/     # application logs + pcaps (timestamped when persistence.preserveOldLogs)
├── current -> ./20260730-121500
├── o1-adapter.log
└── netconf.log
```

Notes:

- Output still reaches pod stdout, so `kubectl logs` keeps working unchanged.
- The adapter timestamps its own lines, so they are copied verbatim — including the ANSI
  colour codes around the log level, so read that file with `less -R`. The netconf-server
  emits no timestamps, so its lines are prefixed with `[YYYY-MM-DD HH:MM:SS]` on the way to
  the file.
- The files are appended to (`tee -a`) and are **not** rotated or timestamp-foldered like
  the application logs — one file per sidecar, growing across restarts.
- They only survive pod restarts when `persistence.enabled` is true; otherwise the volume
  is an `emptyDir`.
